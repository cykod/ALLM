# ALLM v0.3 — Image Generation, Editing & Vision Implementation Phasing

## Approach

This phasing slices spec [§35](steering/allm_engine_session_streaming_spec_v0_2.md#35-v03--image-generation-and-image-processing) — the v0.3 image extension — into ordered, independently shippable phases on top of the now-complete v0.2 runtime foundation (`ALLM.Engine`, `ALLM.Session`, the `Adapter`/`StreamAdapter` behaviours, the bundled OpenAI/Anthropic providers, the §31 Fake-driven test harness, and the provider-neutral examples gate). Nothing in v0.3 changes streaming, sessions, tool orchestration, or the existing chat adapters' wire shape — image generation is parallel to the chat pipeline (§35.1) and vision content parts (§35.6) are a strictly additive Layer A change with backward-compat string normalization.

The key constraint shaping the order is **non-streaming first, vision second**. §35.2 is request/response, so it lands without re-litigating the §3 stream-first invariant; once `ALLM.generate_image/3` works end-to-end against `ALLM.Providers.FakeImages`, the OpenAI Images adapter is a single self-contained phase. Vision (§35.6) is a separate Layer A change that touches the *existing* chat adapters and is therefore phased *after* the image core ships, so a regression in the multimodal content-part normalization cannot break image generation. The second constraint is **opt-in per engine** (§35.3 design goal #3): an engine without `image_adapter:` returns `{:error, :no_image_adapter}` from image calls and is otherwise unchanged — so v0.3 is fully backward-compatible with every v0.2 caller and the engine serializability invariant from Phase 2/8 of v0.2 must continue to hold (verified in Phase 1 here).

### Principles

1. **Parallel pipelines, not entangled.** §35.1 design goal #1 is the spine: `ALLM.ImageAdapter`, `ALLM.ImageRequest`, `ALLM.ImageResponse`, and `ALLM.ImageUsage` are separate types from their chat counterparts. A phase that proposes folding image dispatch into `ALLM.Adapter` or wiring `ALLM.Engine.adapter` as a fallback for image calls is wrong-shaped; reject it before design.
2. **Stream-first does not apply to images.** §35.1 design goal #2 explicitly rules out a `stream_generate_image/3`. The v0.2 stream-equivalence invariant (§3) is silent here. Provider-specific partial-preview features (if a provider exposes them) ride in `ImageRequest.options` and must not surface as `ALLM.Event` variants.
3. **TDD with `FakeImages` as the test vehicle.** Network mocks are banned except when testing a real adapter's wire shape — same rule as v0.2. Recorded fixtures live under `test/fixtures/openai/images/` for the OpenAI Images adapter and are played through a mock Finch transport. Live-API smoke tests are gated on `OPENAI_API_KEY` and skipped in CI by default.
4. **Backward-compat is a test, not a comment.** Every v0.3 phase that touches a Layer A struct used by v0.2 (notably `ALLM.Message.content` in Phase 5) lands with an explicit "v0.2 callers unchanged" test that builds a `String.t()` content message and asserts it serializes/deserializes/dispatches identically to v0.2 behaviour. Phase 1 also re-runs the v0.2 engine round-trip suite with `image_adapter:` populated to prove the new field doesn't perturb existing serializability.
5. **Cite §35 sub-section numbers, don't re-state them.** `# per §35.4 image_adapter is opt-in`, `# §35.6 ImagePart detail field maps to OpenAI input_image detail`. The v0.2 spec is the canonical source; phase docs and code reference it.
6. **Every bundled provider adapter ships with a runnable example.** New scripts go into the existing `examples/` framework (next free index — `10_*.exs` onward) using the `_helpers.exs` pattern; `run_all.exs` is extended and its exit-0 against both providers (where applicable — Anthropic has no image-generation adapter per §35.7) remains the BLOCKING `/review` gate. Live cost ~$0.05–0.20/run for image generation given gpt-image-1 pricing; budget accordingly.
7. **Cross-phase bug discipline (carries over from v0.2).** When a sub-phase uncovers a bug in earlier-phase code, document it in the retro and (if a workaround fits) record it inline. Do NOT fix outside the current phase's scope unless the design explicitly says so.
8. **No `Image.from_url/1` HTTP fetching at construction time.** `ALLM.Image{source: {:url, _}}` carries the URL as data; the adapter is responsible for either passing the URL through to the provider or downloading it at request-build time. Doing eager fetches in `from_url/1` would (a) make `Image` non-serializable in practice and (b) hide latency behind a constructor — both anti-patterns relative to v0.2's Layer A discipline.

### What Each Phase Delivers

Every phase produces, at minimum:

- A `/design` document under `steering/PHASE_13_<slug>.md` (continuing v0.2's numbering — Phases 1–12 are taken) referencing this file and the relevant §35.x sub-section numbers.
- Green `mix test` with ≥80% global coverage and ≥90% on new code; zero `unused_var` warnings.
- `mix credo --strict` clean on changed files; `mix dialyzer` clean against the prior PLT.
- `mix format --check-formatted` clean.
- `@spec` on every new public function; `@doc` with at least one runnable doctest on every public function.
- For Layer A changes: serializability round-trip tests (`:erlang.term_to_binary/1` + `Jason` via `ALLM.Serializer`).
- For behaviour changes: an updated conformance suite under `test/support/` that the corresponding `Fake*` adapter passes unchanged.
- A `CHANGELOG.md` entry per public-API change.
- Commit messages citing the §-number the phase implements (e.g., `feat(images): generate_image facade per §35.5`).
- For phases that touch a real provider adapter: at least one runnable script under `examples/` and an updated `run_all.exs`.

## Phase 1: Layer A Image Data — Structs, Facade, Validators

The image pipeline begins with four new Layer A structs (`ALLM.Image`, `ALLM.ImageRequest`, `ALLM.ImageResponse`, `ALLM.ImageUsage` per §35.2.1–§35.2.4) plus the facade constructor `ALLM.image_request/2` (§35.5) and the new `ALLM.Validate.image_request/1` validator (analogous to the existing §16 validators already implemented in v0.2). These structs must round-trip through `:erlang.term_to_binary/1` and through `Jason` via `ALLM.Serializer`, including every legal `ALLM.Image.source` shape (`{:binary, _}`, `{:base64, _}`, `{:url, _}`, `{:file, _}` — the file form is documented as opaque per §35.2.1 and the round-trip test asserts the path is preserved verbatim, not that the file contents are read). `ALLM.Engine` gains the new `image_adapter: module() | nil` field (§35.4), with a serializability round-trip test that adds an `image_adapter:` to an existing engine fixture and asserts every v0.2 invariant from `lib/allm/engine.ex` continues to hold.

Key behaviours: the operation-arity constraints from §35.2.2 (`:generate` requires prompt + empty input_images; `:edit` requires prompt + 1–2 input_images, optional mask; `:variation` requires exactly one input_images entry, prompt nil/ignored) live in `ALLM.Validate.image_request/1` returning `:ok | {:error, %ALLM.Error.ValidationError{}}` with closed-enum reasons (`:image_request_missing_prompt`, `:image_request_invalid_input_count`, `:image_request_unexpected_prompt`). `ALLM.Image` ships its constructors (`from_file/1`, `from_binary/2`, `from_url/1`, `from_base64/2`) as pure data — no HTTP, no `File.read!/1` (per principle #8); the adapter handles I/O. `to_binary/1` resolves `{:file, _}` and `{:base64, _}` to bytes; `to_data_uri/1` produces `data:<mime>;base64,<...>` strings. `ImageUsage` carries optional token fields per §35.2.4 because gpt-image-1 charges both image units AND tokens — `Decimal.t() | nil` cost fields populate from `llm_db` when present (§6.3) and are `nil` otherwise.

**Delivers:** `lib/allm/image.ex`, `lib/allm/image_request.ex`, `lib/allm/image_response.ex`, `lib/allm/image_usage.ex`; `image_request/2` constructor in `lib/allm.ex`; `ALLM.Validate.image_request/1` extending `lib/allm/validate.ex`; the `:image_adapter` field on `ALLM.Engine` (struct-only — no dispatch yet); round-trip tests for all four structs through `:erlang.term_to_binary/1` and `Jason`; engine round-trip test asserting `image_adapter:` doesn't break v0.2 serializability invariants; doctests on every public constructor and validator. ≥90% coverage on new code.

**Key decisions to make:** (a) Whether `ALLM.Image.to_binary/1` for `{:url, _}` returns `{:error, :remote_source}` (forcing the adapter to fetch) or attempts a `Req` GET. The principle says the latter is wrong (eager fetches in constructors); make the call explicit. (b) Whether the `ValidationError.reason` enum extends with a single `:invalid_image_request` umbrella or four distinct atoms. Distinct atoms are more useful for telemetry and error-routing in Phase 4 — match v0.2's precedent.

## Phase 2: `ALLM.ImageAdapter` Behaviour + Conformance + `FakeImages`

The behaviour and the deterministic test vehicle land together so every subsequent phase has a backbone to test against. `ALLM.ImageAdapter` (§35.3) declares `generate/2`, `prepare_request/2` (optional escape hatch), and `supported_operations/0`. The conformance suite under `test/support/image_adapter_conformance.ex` asserts every implementation: (a) returns `{:error, {:unsupported_operation, op}}` for operations not in `supported_operations/0` *before* any HTTP call, (b) preserves `request_id` from `opts` onto the response, (c) round-trips `metadata:` from request → response unchanged when the adapter doesn't have a use for it. `ALLM.Providers.FakeImages` (§35.8) passes the conformance suite and ships scripted-response fixtures under `test/support/fake_image_fixtures.ex` covering: single-image generation, multi-image batch (`n: 4`), edit with mask, variation, exhausted-script `{:error, :no_scripted_image}`, model-aware operation rejection (e.g., a script declaring `supported_operations: [:generate]` returning unsupported_operation for `:edit`), and the `gpt-image-1`-style usage shape with both token and image-unit fields.

Key behaviours: scripted responses are plain data (a list of `%ALLM.Image{}` plus an optional `usage:` per call) loaded into adapter state via `ALLM.Providers.FakeImages.script/1` before the call. State is process-local (default to `Process.put/2` under a namespaced key, matching the chat-side Fake's pattern from v0.2 — adjust to `Agent`-backed if parallel test isolation demands it). The conformance suite is published as a test-support module that downstream packages implementing `ALLM.ImageAdapter` (Stability, Replicate, fal.ai per §35.7) can `use` to validate their own implementations — same "publish the conformance" decision as v0.2 Phase 3.

**Delivers:** `lib/allm/image_adapter.ex` behaviour with full `@spec` and `@doc`; `lib/allm/providers/fake_images.ex` implementing it; `test/support/image_adapter_conformance.ex` conformance macro; `test/support/fake_image_fixtures.ex` with at least seven named fixtures covering the cases above; conformance suite passes against `FakeImages`; doctests on `FakeImages.script/1`. ≥90% coverage.

**Key decisions to make:** (a) Whether `supported_operations/0` is per-module (one list for the adapter) or per-call (model-aware: `dall-e-3` is generate-only while `gpt-image-1` supports generate + edit). The latter is the Phase 6 reality; the former is simpler. Resolve here: per-module list of *all* operations the adapter can perform, plus a per-model gate that the adapter applies internally before dispatch. The conformance test asserts the per-module list is honored; the per-model check is OpenAI-Images-specific in Phase 6.

## Phase 3: Engine Wiring + Public API — `generate_image/3 · edit_image/4 · image_variations/3`

This is the first phase that delivers user-visible value: an engine constructed with `image_adapter: ALLM.Providers.FakeImages` produces real `%ALLM.ImageResponse{}` values from `ALLM.generate_image/3`. The implementation in `lib/allm.ex` is a thin `with` chain — validate the request (Phase 1), resolve the model and key via `ALLM.Keys.get!/2` at adapter-call time (§6.4 — keys never live on the engine), check `engine.image_adapter` is non-nil (else `{:error, %ALLM.Error.EngineError{reason: :no_image_adapter}}`), and dispatch to `engine.image_adapter.generate(request, opts)`. `ALLM.edit_image/4` and `ALLM.image_variations/3` are sugar that build the appropriate `%ALLM.ImageRequest{}` (`operation: :edit | :variation`) and delegate to `generate_image/3`. The string-prompt sugar from §35.5 (`generate_image(engine, "a watercolor kestrel", size: ...)`) lives here and lifts the keyword opts into `ImageRequest` fields. None of this phase touches a real network — every test runs against `FakeImages`.

Key behaviours: `request_id` is generated once at the top of `generate_image/3` (matching v0.2 Phase 9's correlation-ID pattern) and propagates onto `ImageResponse.request_id`. `merge_opts/2` from `ALLM.Engine` (already implemented in v0.2) is the single place where call-site opts combine with engine defaults, including `:model` resolution — `model:` on the `ImageRequest` overrides `engine.model`, which overrides the application config. The `:no_image_adapter` error is a closed-enum `EngineError` reason; v0.2's `EngineError` already carries this kind of vocabulary, so this is a one-line `@type` extension. `ALLM.image_request/2` accepts a prompt string + keyword opts and returns a fully-populated `%ALLM.ImageRequest{}` ready for dispatch.

**Delivers:** `ALLM.generate_image/3 · edit_image/4 · image_variations/3` in `lib/allm.ex` with full doctests against `FakeImages`; `:no_image_adapter` reason added to `ALLM.Error.EngineError`; integration tests covering happy path (single + multi-image), validation failure (missing prompt, wrong input_image count), missing image_adapter, and string-prompt sugar; round-trip test asserting `generate_image/3 |> Map.from_struct()` and `edit_image/4 |> ...` produce the same `ImageRequest` shape that explicit construction would. ≥90% coverage.

**Key decisions to make:** (a) Whether `edit_image/4` accepts `[ALLM.Image.t()]` for inpaint-with-mask (two images: base + mask) as a list, or insists on the `mask:` keyword. The spec §35.5 signature is `ALLM.Image.t() | [ALLM.Image.t()]`; the cleanest call site is `edit_image(engine, base, "make the sky pink", mask: my_mask)`. Resolve in design.

## Phase 4: Telemetry, Capability Pre-flight, Retry for Image Calls

Cross-cutting concerns that mirror v0.2 Phase 9's pattern. `ALLM.Telemetry` (already implemented in v0.2) gains two new event spans per §35.9: `[:allm, :image, :start]` (measurements: `system_time`; metadata: `request_id`, `operation`, `model`, `n`) and `[:allm, :image, :stop]` (measurements: `duration`, `image_count`; metadata: `request_id`, `operation`, `model`, `usage`, `error`). `ALLM.Capability.preflight/2` extends to handle `ImageRequest`: when `llm_db` is loaded, it validates that the resolved model declares `images_enabled` and that the requested operation is in the model's supported set; when `llm_db` is absent it's a no-op (verified by the existing dep-free smoke test from v0.2 Phase 9, extended to cover the new image path). `ALLM.Retry` (also from v0.2) wraps the adapter call with the existing 429/5xx backoff policy — image generation is non-streaming so the retry budget applies cleanly without the "stream is partly consumed" exclusion.

Key behaviours: telemetry events fire even on validation failure (the `:error` metadata field carries the validation struct), so observability is uniform across success and failure paths — same contract as v0.2's chat telemetry. Capability pre-flight runs entirely off the `llm_db` catalog and never makes network calls; an `:unsupported_capability` `ValidationError` (vocabulary already defined in v0.2 Phase 9) carries which capability failed (`:image_generation`, `:image_edit`, `:image_variation`). Retries use the same `Retry-After` parser as the chat retry path, so OpenAI's 429 + retry-after headers on the images endpoint behave identically to chat.

**Delivers:** Two new telemetry spans wired into `ALLM.generate_image/3`; capability pre-flight extended to `ImageRequest` with the dep-free smoke test extended; retry integration with `ALLM.Providers.FakeImages.script/1` adding a `retry_until_call: n` option matching the chat-side Fake's pattern; tests with `:telemetry_test.attach_event_handlers/2` asserting expected events fire in order on success, validation failure, and after-retry success; `:unsupported_capability` propagation tests for image operations. ≥90% coverage on changed code.

**Key decisions to make:** (a) Whether the `[:allm, :image, :stop]` event's `image_count` measurement is the `n` from the request (what was asked) or `length(response.images)` (what was returned). Returning the actual count is more useful for cost/observability dashboards, but the request `n` is available even on error paths — pick one and document. (b) Whether `Retry` jitter parameters from v0.2 are reused as-is or get image-specific tuning (gpt-image-1 calls take 5–30s; the v0.2 backoff was tuned for chat's sub-5s requests).

## Phase 5: Multimodal Content Parts — `ALLM.TextPart` + `ALLM.ImagePart`

The first Layer A change in v0.3 that touches existing v0.2 code: `ALLM.Message.content` (currently `String.t() | list(map())`) widens to `String.t() | [ALLM.TextPart.t() | ALLM.ImagePart.t()]` per §35.6. `ALLM.TextPart` is a `%{text, metadata}` struct; `ALLM.ImagePart` carries `%{image: ALLM.Image.t(), detail: :auto | :low | :high, metadata}`. Backward compatibility is the load-bearing test: every v0.2 chat message-construction path (`ALLM.user/1`, `ALLM.system/1`, `ALLM.assistant/1`, `ALLM.tool_result/2`) continues to accept and produce `String.t()` content unchanged, and a normalization helper `ALLM.Message.normalize_content/1` lifts a string to `[%TextPart{text: s}]` exactly when an adapter (Phases 7–8) needs the structured form. The existing untyped `list(map())` form from v0.2 is *removed* — there are no v0.2 callers that rely on it (verified by `grep` over `lib/`, `test/`, and `steering/examples/` in the design phase) and keeping a third shape would force every adapter to handle three input types instead of two.

Key behaviours: the v0.2 `ALLM.Message` round-trip serializability test gets re-run with messages containing `[TextPart, ImagePart]` content — the test expands to cover all four legal `ALLM.Image.source` shapes inside an `ImagePart`. `ALLM.Validate.message/1` (already in v0.2's `lib/allm/validate.ex`) extends to validate part lists (each element is a `TextPart` or `ImagePart`; no other shapes; non-empty list when content is `[]`-typed). The OpenAI chat adapter (Phase 7) and Anthropic chat adapter (Phase 8) consume the structured form; this phase ships *only* the structs and normalization, deliberately not wiring them into adapters yet, so a regression here can be localized.

**Delivers:** `lib/allm/text_part.ex`, `lib/allm/image_part.ex`; updated `@type` on `ALLM.Message.content`; `ALLM.Message.normalize_content/1` helper; extended `ALLM.Validate.message/1`; full v0.2 backward-compat test suite (every existing message construction unchanged); round-trip serializability for messages with mixed content lists; doctests. The list-of-untyped-maps form is removed with a CHANGELOG entry flagging it. ≥90% coverage on new code.

**Key decisions to make:** (a) Whether `ALLM.user/1` grows a sister `ALLM.user/2` that accepts `(text, images: [...])` for ergonomics, or callers always build `%ALLM.Message{content: [...]}` by hand for multimodal. The former is closer to the v0.2 facade philosophy; the latter is more explicit. (b) Whether `ALLM.ImagePart.detail` defaults to `:auto` (matches OpenAI's default) or `nil` (force the adapter to choose per-provider).

## Phase 6: `ALLM.Providers.OpenAI.Images` — First Real Image Provider

The first real network adapter for image generation. `ALLM.Providers.OpenAI.Images` implements `ALLM.ImageAdapter` against `/v1/images/generations`, `/v1/images/edits`, and `/v1/images/variations` (§35.7) with model-aware operation gating: `gpt-image-1` supports `:generate` + `:edit`, `dall-e-3` supports `:generate` only, `dall-e-2` supports all three. The adapter switches on `request.operation` to pick the endpoint, and on `request.model` to validate the operation is supported by that model — if not, returns `{:error, {:unsupported_operation, op, model}}` *before* any HTTP call (asserted by the conformance suite from Phase 2). `request.response_format` (`:binary | :base64 | :url`) maps to the OpenAI `response_format` body field with one wrinkle: gpt-image-1 always returns base64 regardless and the adapter normalizes that into the requested form by base64-decoding to `:binary` when the caller asked for binary. Recorded fixtures under `test/fixtures/openai/images/` cover happy path × three operations × three models, 429 with `Retry-After`, 5xx, malformed response, missing-image-in-response, and gpt-image-1's token-usage shape (`input_tokens` + `output_tokens` populated alongside `images: 1`).

Key behaviours: the multipart/form-data construction for `:edit` and `:variation` (which take an actual image file payload in the request body) lives in a private helper; `ALLM.Image.to_binary/1` from Phase 1 resolves `{:file, _}` and `{:base64, _}` to bytes for the multipart wrapper. URL-source images on `:edit`/`:variation` are downloaded by the adapter at request-build time (per principle #8 — eager fetches happen at the boundary, not in constructors). API key resolution goes through `ALLM.Keys.get!/2`; no key is baked. A live-API smoke test gated on `OPENAI_API_KEY` covers `:generate` against `dall-e-2` (cheapest at ~$0.018/image so ~$0.05/run) and writes the resulting PNG to a tmp file the test verifies decodes.

**Delivers:** `lib/allm/providers/openai/images.ex` implementing `ALLM.ImageAdapter`; recorded-fixture wire tests across the 3×3 operation/model matrix plus error classes; multipart/form-data builder; URL-source eager-download path; live smoke test against `dall-e-2`; conformance suite passes unchanged; `usage` mapping from OpenAI's response shape into `ALLM.ImageUsage` (including gpt-image-1's token fields when present); `examples/10_generate_image.exs` (smallest reproducer using `dall-e-2`) and an updated `run_all.exs`. ≥90% coverage on new code.

**Key decisions to make:** (a) Whether to expose OpenAI's `user:` parameter (request-level user identifier for abuse monitoring) and `style: :natural | :vivid` (DALL-E 3 only) on `ImageRequest` directly or through `ImageRequest.options`. The spec already lists `style` in §35.2.2 — wire it through. `user:` is OpenAI-specific — `options` is the right shape. (b) Whether the adapter shares the `ALLM.Providers.Support.SSE` helper from v0.2 — it does not (no streaming) — but it does share `ALLM.Providers.Support.Headers` (auth-header builder) if such a module exists; if not, factor the auth-header construction out so the future Stability/Replicate third-party adapters can reuse it.

## Phase 7: Vision Input in `ALLM.Providers.OpenAI` Chat Adapter

The first phase that wires `ALLM.ImagePart` (Phase 5) end-to-end on the chat side. The OpenAI chat adapter (`lib/allm/providers/openai.ex`, already implementing both Chat Completions and Responses APIs from v0.2 Phase 10) gains a content-part translator: `TextPart` → `{type: "input_text", text: ...}` (Responses) or `{type: "text", text: ...}` (Chat Completions), `ImagePart` → `{type: "input_image", image_url: <data-uri-or-url>, detail: ...}` (Responses) or `{type: "image_url", image_url: %{url: ..., detail: ...}}` (Chat Completions). The wire-shape difference between the two endpoints is a small dispatch table; both forms accept either a public URL or a data URI built via `ALLM.Image.to_data_uri/1`, so the translator is endpoint-agnostic at the source level. Recorded fixtures cover a vision request with a single image + text, multiple images, base64-source vs URL-source vs file-source images, and the existing v0.2 string-content path (which goes through `ALLM.Message.normalize_content/1` from Phase 5).

Key behaviours: assistant responses from vision-capable models that contain image *outputs* (rare today, but supported by some models) deserialize back into `[ALLM.TextPart, ALLM.ImagePart]` content lists — the same translator runs in both directions. Image size limits and supported MIME types per OpenAI's docs are validated at the adapter boundary (`image/png`, `image/jpeg`, `image/webp`, `image/gif`; ≤20 MB per image — anything else returns `{:error, %ALLM.Error.ValidationError{reason: :unsupported_image_format | :image_too_large}}` with the offending image's index). The v0.2 chat-equivalence and stream-equivalence properties from Phase 5/7 of v0.2 must continue to hold with vision content — the property tests are extended with a fixture that includes an `ImagePart` and asserts `chat ≡ stream |> StreamCollector.to_chat_result`.

**Delivers:** Content-part translator in `lib/allm/providers/openai.ex` covering both endpoints; recorded-fixture wire tests for vision against both Chat Completions and Responses; assistant-side image-output decoder (with explicit "no current model emits this in our test matrix; deserializer is future-proofing" doc note); MIME and size validation at the adapter boundary; v0.2 stream-equivalence properties extended with vision; live smoke test against `gpt-4o-mini` (vision-capable + cheap) gated on `OPENAI_API_KEY` (~$0.01/run); `examples/12_vision_input.exs` and updated `run_all.exs` (the OpenAI arm). ≥90% coverage on new code.

**Key decisions to make:** (a) Whether to validate image size (≤20 MB) by `byte_size/1` of resolved binary, which forces an eager resolve of `{:url, _}` sources — or trust the provider's API-side validation and skip. The principle says no eager fetches; the trade-off is that an oversized URL image fails with a less clear error from OpenAI. Resolve in design — leaning skip with a CHANGELOG note. (b) Whether the data-URI path is used by default for `{:base64, _}` and `{:binary, _}` and the URL path is used for `{:url, _}`, or always URL when the source is a URL with size ≤256 KB. Defaults matter for latency.

## Phase 8: Vision Input in `ALLM.Providers.Anthropic` Chat Adapter

Mirror of Phase 7 for Anthropic. The Anthropic chat adapter (`lib/allm/providers/anthropic.ex`, from v0.2 Phase 11) gains an analogous translator: `TextPart` → `{type: "text", text: ...}`, `ImagePart` → `{type: "image", source: {type: "base64", media_type: ..., data: ...}}` for `{:binary, _}` and `{:base64, _}` sources, or `{type: "image", source: {type: "url", url: ...}}` for `{:url, _}` sources (Anthropic added URL image support in mid-2025; verify the API still accepts it at design time). The §33 v0.2 non-goal of "vision" is no longer a non-goal — the adapter's Phase 11 `:vision_not_in_v0_2` `ValidationError` rejection (introduced as a placeholder in v0.2) is removed and replaced with the real translator. System messages remain extracted as a top-level `system` parameter, unchanged from v0.2. Recorded fixtures cover the same matrix as Phase 7's OpenAI vision tests — single image + text, multiple images, all four `Image.source` shapes, plus a fixture exercising the long-content (>64KB) HTTP/1 flow-control bug from §7.2 to confirm Finch is still HTTP/1 in the non-streaming Req path (it is — chat-side image messages go through `Req`, not Finch — but the test pins it).

Key behaviours: Anthropic's vision API supports `image/jpeg`, `image/png`, `image/gif`, `image/webp`. Anthropic does *not* have an equivalent of OpenAI's `detail` field; the `ALLM.ImagePart.detail` is dropped at the adapter boundary with a one-line debug log (deferred form per the CLAUDE.md hot-path Logger rule). The v0.2 stream-equivalence property is extended with an Anthropic vision fixture, mirroring Phase 7. The Phase 11 retro flagged that Anthropic's tool-forcing pattern for structured output and the streamed `text_delta` rewriting (Phase 11.3 M1 fix) interact with response shape — a regression test confirms vision + structured output still byte-matches between streaming and non-streaming arms.

**Delivers:** Content-part translator in `lib/allm/providers/anthropic.ex`; removal of the v0.2 placeholder `:vision_not_in_v0_2` rejection (CHANGELOG-flagged as a behaviour change for any caller relying on the rejection); recorded-fixture wire tests; v0.2 stream-equivalence properties extended; v0.2 structured-output + vision interaction regression test; live smoke test against `claude-haiku-4-5-20251001` (vision-capable + cheap) gated on `ANTHROPIC_API_KEY` (~$0.01/run); updated `run_all.exs` (the Anthropic arm). ≥90% coverage.

**Key decisions to make:** (a) Whether `ImagePart.detail` being silently dropped is acceptable, or whether the adapter emits a one-time warning per process that detail is not supported by Anthropic. A warning is more discoverable; silent drop matches the principle that adapters translate to provider shapes. (b) Whether to add an Anthropic-only `cache_control` annotation pass for image parts (Anthropic supports caching expensive image inputs across messages). The spec doesn't scope prompt caching for v0.3; this is a v0.4 candidate — defer.

## What Comes After

v0.3 is the **multimodal foundation**. Post-release candidates for v0.4 and beyond, all flagged in §32.5 / §33 / §35.10:

- **Audio input/output** — speech-to-text, text-to-speech as separate Layer C surfaces parallel to image (`ALLM.transcribe/3`, `ALLM.synthesize/3`).
- **Embeddings** — `ALLM.embed/3` against `/v1/embeddings` and Anthropic's voyage equivalents.
- **Streaming image previews** — provider-specific partial-image events; would require widening the §3 stream-first invariant or adding a separate `ImageEvent` union.
- **Prompt caching** as a first-class API surface (Anthropic + OpenAI both support it now).
- **Middleware (§29)** — populating `Engine.middleware: []` with a composable middleware chain. Still deferred from v0.2.
- **Memory stores** — pluggable conversation memory beyond raw `Thread` persistence.
- **Additional provider adapters** — Gemini (image + chat + vision), Stability/Replicate/fal.ai (image-only), local LLMs (Ollama, llama.cpp). Each is a standalone phase or a separate package per §32.

Phases in this document build **toward** that boundary, not past it. If a phase finds itself designing a streaming-image protocol, an audio adapter, or an embeddings surface, the phase scope is wrong — push the feature into a v0.4 design doc and finish the v0.3 phase with only what §35.x sub-sections require.
